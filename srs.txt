System Name: Prompt Injection Attack Simulator & Webpage Scanner
Document Version: 1.0
Document Date: June 14, 2026
Document Status: Initial Technical Baseline


1. INTRODUCTION

1.1 Purpose

This Software Requirements Specification defines the functional behavior,
interfaces, architecture, data structures, security controls, quality
attributes, and verification requirements for the Prompt Injection Attack
Simulator & Webpage Scanner.

1.2 Intended Audience

- Software developers
- QA and security testers
- Project reviewers
- DevOps engineers
- AI security researchers
- Technical project supervisors

1.3 System Scope

The system receives a URL or HTML file, obtains static HTML, extracts visible
and hidden text-bearing sources, detects suspicious natural-language
instructions, calculates a risk score, returns structured findings, and
generates defensive reports.

1.4 Definitions

AI Agent:
An AI system that interprets information and may use tools or take actions.

Indirect Prompt Injection:
An instruction placed in external untrusted content with the intention of
influencing an AI model or agent that later processes that content.

Finding:
A structured record describing suspicious content, its location, evidence,
matched rules, score contribution, impact, and remediation.

Static Scan:
Analysis of received HTML without executing JavaScript or rendering a dynamic
browser DOM.

Hidden Content:
Text not normally visible to a user due to HTML attributes, inline CSS, or
non-visual HTML locations such as comments and metadata.

SSRF:
Server-Side Request Forgery, in which a server is induced to request an
unauthorized internal or sensitive network resource.

3. SYSTEM CONSTRAINTS

SC-001: MVP scans shall not execute retrieved or uploaded JavaScript.

SC-002: MVP URL scans shall analyze a single retrieved HTML document and shall
not crawl linked pages.

SC-003: MVP hidden-style analysis shall support HTML attributes and inline CSS.
External stylesheet and computed-style analysis requires rendered scan mode.

SC-004: All page content shall be treated as untrusted data.

SC-005: Detection results shall be described as heuristic.

SC-006: The system shall not automatically follow instructions detected in
scanned content.

SC-007: The backend shall not send scanned content to an external AI service in
the MVP.


4. COMPONENT REQUIREMENTS

4.1 Frontend Application

The frontend shall:

- Capture URL and file inputs.
- Submit scans to the backend.
- Display progress, errors, and completed results.
- Render evidence as escaped text.
- Provide score, severity, filters, and recommendations.
- Display and launch demo scans.
- Request report generation.
- Display scan history when enabled.

Suggested pages:

- /                Dashboard
- /scan            Scanner
- /results/:id     Results
- /demo            Demo Lab
- /reports/:id     Report preview
- /about           Methodology and limitations

4.2 API Application

The FastAPI application shall:

- Validate request data.
- Enforce upload and response limits.
- Retrieve public HTTP/HTTPS targets securely.
- Parse and analyze HTML.
- Return consistent JSON responses.
- Generate reports.
- Expose demo page metadata.
- Apply security middleware and configured CORS policy.

4.3 Secure URL Fetcher

The fetcher shall:

- Accept only http and https schemes.
- Reject URLs containing credentials.
- Reject empty or malformed hostnames.
- Normalize internationalized domain names safely.
- Resolve DNS before connection.
- Reject any resolved non-public IP address.
- Revalidate every redirect target.
- Apply connection, read, write, and total timeouts.
- Enforce a maximum redirect count.
- Limit allowed destination ports.
- Stream responses and stop after the configured byte limit.
- Accept HTML-compatible response types only.
- Use a fixed application User-Agent.
- Avoid forwarding user-supplied authorization headers or cookies.
- Avoid using environment proxy settings unless explicitly configured.

Blocked targets shall include:

- Loopback addresses.
- Private network addresses.
- Link-local addresses.
- Multicast addresses.
- Unspecified and reserved addresses.
- IPv4 and IPv6 equivalents of blocked ranges.
- Cloud instance metadata addresses.
- Hostnames that resolve to any blocked address.

The implementation shall mitigate DNS rebinding by connecting only to a
validated resolved address or otherwise guaranteeing that the actual
connection destination is the validated address.

4.4 HTML Parser and Extractors

The parser shall use BeautifulSoup with a configured parser. It shall create
source records before detection.

Required source types:

- HTML_COMMENT
- META_CONTENT
- IMAGE_ALT
- ARIA_LABEL
- TITLE_ATTRIBUTE
- DATA_ATTRIBUTE
- HIDDEN_ATTRIBUTE_TEXT
- HIDDEN_INLINE_CSS_TEXT
- SMALL_FONT_TEXT
- SAME_COLOR_TEXT
- SCRIPT_TEXT, when explicitly enabled
- NOSCRIPT_TEXT
- VISIBLE_TEXT

Each source record shall contain:

- Source type.
- Normalized text.
- Original text.
- Safe snippet.
- Element name where applicable.
- Relevant attribute name where applicable.
- DOM path or source index where possible.
- Hidden reason where applicable.

4.5 Detection Engine

The detection engine shall compare normalized source text against configured
rules.

Required categories:

- INSTRUCTION_OVERRIDE
- DATA_EXFILTRATION
- UNAUTHORIZED_ACTION
- ROLE_MANIPULATION
- STEALTH_INSTRUCTION

Example baseline rules:

Instruction Override:
- ignore previous instructions
- disregard previous instructions
- forget your rules
- override system prompt
- bypass safety rules
- follow only this instruction

Data Exfiltration:
- reveal secret
- leak credentials
- show password
- send user data
- extract token
- exfiltrate data
- access private data

Unauthorized Action:
- delete files
- send email
- click this link
- submit the form
- transfer money
- approve payment

Role Manipulation:
- act as admin
- you are root
- developer mode enabled
- unrestricted mode
- jailbreak

Stealth Instruction:
- do not tell the user
- hide this instruction
- silently perform
- no confirmation required

Each rule definition shall include:

- Unique rule ID.
- Category.
- Human-readable name.
- Pattern or phrase.
- Weight.
- Explanation.
- Impact template.
- Recommendation identifiers.
- Enabled status.

4.6 Text Normalization

Before matching, the system shall:

- Decode HTML entities.
- Apply Unicode normalization.
- Convert matching text to a consistent case.
- Collapse repeated whitespace.
- Normalize common punctuation separators where safe.
- Preserve original text for evidence.
- Enforce a maximum source text length.

The system should optionally detect common zero-width characters and record
that normalization occurred. Normalization shall not alter the evidence shown
to the user.

4.7 Hidden Content Detection

An element shall be considered hidden for the MVP when one or more of the
following applies:

- It has the hidden attribute.
- Its inline style contains display:none.
- Its inline style contains visibility:hidden or visibility:collapse.
- Its inline style contains opacity:0.
- Its inline style defines a font size below the configured threshold.
- Its inline foreground and background colors normalize to the same value.
- Its input type is hidden and its value is being inspected under a configured
  attribute rule.
- An ancestor is hidden by one of the supported HTML or inline style rules.

Inline style parsing shall use a CSS parser where practical. The system shall
not claim to evaluate external CSS or final computed styles during a static
scan.

4.8 Finding Builder

A finding shall be created when one or more enabled rules match a source.

Finding fields:

- id
- scan_id
- title
- severity
- location
- source_type
- category
- payload
- snippet
- element
- attribute
- dom_path
- hidden_reason
- matched_rules
- reason
- impact
- remediation
- score_contribution
- confidence

Finding IDs shall be stable within the scan and formatted as PI-001, PI-002,
and so on.

Findings shall be deduplicated using a stable combination of source identity,
normalized payload, and matched rule identifiers.

4.9 Risk Engine

The risk engine shall calculate scores using configurable source and rule
weights.

Suggested formula:

finding_score =
    source_location_weight
    + highest_matched_rule_weight
    + category_adjustments

scan_score =
    sum(unique finding scores)
    + additional_unique_source_bonus

final_score = minimum(100, maximum(0, scan_score))

The implementation may refine the formula, but it shall:

- Remain deterministic.
- Avoid duplicate inflation.
- Be covered by boundary tests.
- Return a breakdown.
- Cap the final score at 100.

Severity mapping:

- 0 to 20: Low
- 21 to 50: Medium
- 51 to 80: High
- 81 to 100: Critical

Finding severity may be derived from its individual score using configured
thresholds. Scan severity shall always derive from the final scan score.

4.10 Recommendation Engine

The recommendation engine shall map source types and detection categories to
actionable controls, including:

- Strip HTML comments before LLM ingestion when comments are unnecessary.
- Exclude hidden content from summarization inputs.
- Sanitize metadata, alt text, ARIA text, titles, and data attributes.
- Keep system and developer instructions separate from untrusted page data.
- Mark external content clearly as data, not instructions.
- Restrict agent tools through allowlists.
- Apply least-privilege permissions.
- Require explicit user confirmation for sensitive actions.
- Validate tool arguments independently of model output.
- Log and monitor AI-agent actions.
- Prevent secrets from entering model context unnecessarily.
- Apply output checks and policy enforcement outside the model.

4.11 Report Generator

The report generator shall receive a validated scan result object and create a
self-contained HTML report.

Required report sections:

- Report title.
- Executive summary.
- Scan target.
- Scan date and identifier.
- Overall score and severity.
- Severity and category summary.
- Technical findings.
- Evidence.
- Impact.
- Recommendations.
- Methodology.
- Limitations.
- Defensive-use disclaimer.

Report security requirements:

- Escape all dynamic content.
- Do not include executable user scripts.
- Do not fetch untrusted remote assets.
- Use local or embedded styles.
- Use a restrictive Content Security Policy when served in a browser.
- Sanitize filenames used in download headers.

4.12 Persistence Layer

Persistence is optional for the MVP. When enabled, it shall store:

- Scan identifier.
- Scan type.
- Sanitized target display value.
- Filename or URL as permitted by privacy configuration.
- Timestamp.
- Duration.
- Risk score.
- Severity.
- Finding count.
- Structured findings.
- Scanner version.

Raw uploaded HTML and complete fetched HTML shall not be stored by default.


5. EXTERNAL INTERFACE REQUIREMENTS

5.1 General API Conventions

Base path: /api/v1

Data format: JSON except file upload and downloadable reports.

Timestamps: ISO 8601 in UTC.

Identifiers: UUID for scans and reports.

Successful responses: Appropriate 2xx status.

Validation errors: 422.

Blocked or disallowed target: 400 or 403 according to API policy.

Oversized input: 413.

Unsupported media type: 415.

Retrieval timeout or upstream failure: 502 or 504.

Unexpected server error: 500 with no internal stack trace.

7. DETAILED FUNCTIONAL REQUIREMENTS

7.1 Input Validation

SRS-FR-001: The system shall reject an empty URL.

SRS-FR-002: The system shall reject non-HTTP and non-HTTPS URL schemes.

SRS-FR-003: The system shall reject URLs with embedded credentials.

SRS-FR-004: The system shall reject blocked target addresses before retrieval.

SRS-FR-005: The system shall revalidate redirect destinations.

SRS-FR-006: The system shall reject missing, empty, unsupported, or oversized
HTML uploads.

SRS-FR-007: The system shall not rely only on the client-provided MIME type or
filename extension.

7.2 Retrieval

SRS-FR-008: The system shall retrieve URL content using bounded timeouts.

SRS-FR-009: The system shall stop reading when the maximum response size is
exceeded.

SRS-FR-010: The system shall reject unsupported response content types unless
content inspection confirms acceptable HTML under configured policy.

SRS-FR-011: The system shall record the final validated URL after redirects.

7.3 Parsing and Extraction

SRS-FR-012: The system shall parse malformed but recoverable HTML without
executing it.

SRS-FR-013: The system shall extract all required source types listed in
Section 4.4.

SRS-FR-014: The system shall detect hidden state inherited from supported
ancestor properties.

SRS-FR-015: The system shall preserve original evidence separately from
normalized matching text.

SRS-FR-016: The system shall truncate evidence to a configured display length
while retaining enough context to explain the match.

7.4 Detection

SRS-FR-017: The system shall evaluate every extracted source against all
enabled rules applicable to that source.

SRS-FR-018: The system shall support phrase and regular-expression rules.

SRS-FR-019: The system shall use case-insensitive normalized matching.

SRS-FR-020: The system shall return matched rule IDs for every finding.

SRS-FR-021: The system shall deduplicate equivalent findings.

SRS-FR-022: The system shall not interpret or execute detected instructions.

7.5 Scoring

SRS-FR-023: The system shall compute a score for each finding.

SRS-FR-024: The system shall compute and cap the overall score from 0 to 100.

SRS-FR-025: The system shall map score boundaries exactly as documented.

SRS-FR-026: The system shall return an explainable score breakdown.

7.6 Results and Reports

SRS-FR-027: The frontend shall display overall score, severity, and finding
count.

SRS-FR-028: The frontend shall display each required finding field.

SRS-FR-029: The frontend shall render evidence using text-safe components.

SRS-FR-030: The frontend shall display methodology and limitations.

SRS-FR-031: The backend shall generate a self-contained escaped HTML report.

SRS-FR-032: The report shall reproduce the scan score and finding data without
changing them.


8. SECURITY REQUIREMENTS

SRS-SEC-001: All retrieved and uploaded content shall be treated as untrusted.

SRS-SEC-002: Static scans shall never execute JavaScript, plugins, macros, or
active page content.

SRS-SEC-003: The URL fetcher shall implement the SSRF controls in Section 4.3.

SRS-SEC-004: The system shall validate the actual destination for every
redirect and connection.

SRS-SEC-005: Evidence and target values shall be escaped in the frontend and
reports.

SRS-SEC-006: The production frontend shall use a restrictive Content Security
Policy.

SRS-SEC-007: The API shall configure CORS using an explicit origin allowlist.

SRS-SEC-008: The API shall apply request body and upload size limits.

SRS-SEC-009: Public deployments shall apply rate limiting.

SRS-SEC-010: Production errors shall not expose stack traces, filesystem paths,
environment variables, or dependency secrets.

SRS-SEC-011: Logs shall not include complete uploaded HTML, fetched HTML,
authorization data, cookies, or report evidence by default.

SRS-SEC-012: Report filenames and Content-Disposition values shall be
sanitized.

SRS-SEC-013: Report generation shall not resolve untrusted local paths or
remote URLs.

SRS-SEC-014: Demo scan endpoints shall select files from a fixed allowlist and
shall not accept arbitrary path input.

SRS-SEC-015: Dependencies shall be pinned and scanned for known
vulnerabilities as part of CI.

SRS-SEC-016: If authentication is added, passwords shall use a modern password
hash and sessions or tokens shall be protected according to current framework
guidance.


9. PRIVACY REQUIREMENTS

SRS-PRV-001: Raw HTML shall be held only for the duration required to complete
the scan unless retention is explicitly configured.

SRS-PRV-002: Raw uploaded files shall not be persisted by default.

SRS-PRV-003: The product shall disclose whether scan metadata is retained.

SRS-PRV-004: The system shall provide a deletion mechanism before persistent
multi-user history is released.

SRS-PRV-005: Analytics, if used, shall not capture payload evidence or full
target URLs containing query secrets.


10. PERFORMANCE AND CAPACITY REQUIREMENTS

SRS-PERF-001: The default maximum uploaded HTML size should be 2 MB and shall
be configurable.

SRS-PERF-002: The default maximum fetched response size should be 5 MB and
shall be configurable.

SRS-PERF-003: The default URL total timeout should be 10 seconds and shall be
configurable.

SRS-PERF-004: The default redirect limit should be 3 and shall be configurable.

SRS-PERF-005: A 2 MB uploaded file should complete analysis within 2 seconds on
the documented development reference environment.

SRS-PERF-006: Parsing and detection shall use bounded source and snippet
lengths.

SRS-PERF-007: Public deployment shall use concurrency limits to prevent
resource exhaustion.


11. RELIABILITY AND ERROR HANDLING

SRS-REL-001: Every API error shall follow the error schema in Section 5.9.

SRS-REL-002: Each request shall have a request ID suitable for log
correlation.

SRS-REL-003: A parsing error shall return a controlled response and shall not
crash the service.

SRS-REL-004: Retrieval errors shall distinguish invalid input, blocked target,
timeout, oversized response, unsupported content, and upstream failure.

SRS-REL-005: The service shall remain available after a failed scan.

SRS-REL-006: Database failure shall not expose stored data or credentials in
the response.


12. ACCESSIBILITY AND USABILITY

SRS-UX-001: All form inputs shall have persistent labels.

SRS-UX-002: All interactive controls shall be usable by keyboard.

SRS-UX-003: Focus shall move to the result heading or error summary after a
scan response.

SRS-UX-004: Severity shall include text and shall not rely on color alone.

SRS-UX-005: Loading and error states shall be announced through appropriate
ARIA live regions.

SRS-UX-006: Evidence blocks shall support wrapping and horizontal scrolling
without breaking page layout.

SRS-UX-007: The core workflow shall support viewport widths from 320 pixels
upward.


13. OBSERVABILITY REQUIREMENTS

SRS-OBS-001: The backend shall log request ID, endpoint, status, duration, scan
type, response size category, finding count, and severity.

SRS-OBS-002: Logs shall exclude raw page content by default.

SRS-OBS-003: Production deployments should expose aggregate metrics for scan
count, error count, latency, blocked targets, and severity distribution.

SRS-OBS-004: Health endpoints shall not expose secrets or detailed internal
configuration.


14. CONFIGURATION REQUIREMENTS

The following values shall be environment-configurable:

- Application environment.
- API host and port.
- Allowed frontend origins.
- Maximum upload size.
- Maximum fetched response size.
- URL timeouts.
- Redirect limit.
- Allowed destination ports.
- Rate limits.
- Database URL.
- Scan retention setting.
- Report output setting.
- Detection rule file.
- Risk weight configuration.
- Logging level.

Secrets shall be loaded from environment variables or an approved secret
manager and shall not be committed to source control.

- Very large text nodes.
- Malformed HTML.
- HTML containing script-based DOM injection to verify documented static-scan
  limitations.

18. DEPLOYMENT REQUIREMENTS

SRS-DEP-001: Production traffic shall use HTTPS.

SRS-DEP-002: Debug mode shall be disabled in production.

SRS-DEP-003: Frontend and backend origins shall be explicitly configured.

SRS-DEP-004: The backend shall run with a non-administrative operating-system
identity.

SRS-DEP-005: Containers, if used, shall use a minimal maintained base image.

SRS-DEP-006: CI shall run backend tests, frontend tests, linting, and dependency
security checks.

SRS-DEP-007: Production configuration shall define resource, request, and
concurrency limits.

SRS-DEP-008: Database backups and retention shall be configured before hosted
history is enabled.


19. LIMITATIONS

- Rule-based detection cannot understand every paraphrase or language.
- Static scanning cannot see JavaScript-generated DOM content.
- Inline CSS checks do not represent full browser computed style.
- External stylesheets are not evaluated in the MVP.
- A suspicious phrase may be benign documentation or quoted content.
- A low score does not guarantee safety.
- The scanner estimates content risk; it does not prove whether a particular
  model would obey the detected instruction.

21. DEFINITION OF DONE FOR MVP

The MVP is complete when:

- URL and HTML file scans work through the web interface.
- Required source locations are extracted.
- Required detection categories are implemented.
- Scores and severities are deterministic and tested.
- Results include evidence, explanation, impact, and remediation.
- All six demo pages are available and produce expected findings.
- HTML report export works and safely escapes content.
- SSRF, upload, output-encoding, and size-limit controls are implemented and
  tested.
- Backend and frontend automated tests pass.
- README documents installation, operation, methodology, security model, and
  limitations.
- No known Critical or High severity issue remains in the scanner itself.
